# HDRezka: расследование зависания получения ссылки

Дата: 21.10.2026. Версия патча: `21.10.2026-rezka-v2.2`.

## Результат и границы вывода

**Доказано:** в исходном плагине есть механизм вечного JS-lock: другой запрос вызывает общий `Reguest.clear()`, обработчик потока больше не доставляется, `element.loading` остаётся `true`. Аналогично теряется завершение ленивого плейлиста. Патч устраняет этот механизм и ограничивает ожидание независимым watchdog. Это проверено автоматическими тестами, включая повтор после отказа.

**Вероятно, но не установлено для приставки:** нативные запросы, продолжающиеся после JS-отмены, коллизии request ID или утечки HTTP-ответов могут усиливать сбой. Подтверждённые недостатки upstream перечислены ниже; их причинная связь с наблюдаемым зависанием не доказана.

**Пока неизвестно:** почему помогает перезапуск Xiaomi TV Stick, помогает ли force-stop LAMPA либо Vimu, влияет ли Wi-Fi и «Удержание сокета». Реальной приставки и `adb` в среде нет. Фраза «на Xiaomi исправлено» к этому результату неприменима.

## Что изменено

- `hdrezka.js`: исправления запросов, жизненного цикла, запуска, плейлиста, открытия экрана, регистрации и диагностика.
- `tests/harness.cjs`: управляемые Lampa/Reguest/DOM-моки, fake clock; тестовые точки доступа внедряются только в VM, их нет в production API.
- `tests/hdrezka.test.cjs`: регрессионные сценарии плагина.
- `tests/contracts.test.cjs`, `tests/fixtures/lampa-contracts.cjs`: проверки с дословными фрагментами `native/clear` и обработчика плейлиста из зафиксированного upstream.
- Этот отчёт: baseline, результаты, ограничения и ручной протокол.

Каждая операция получает ID, владельца, поколение и терминальное состояние. Watchdog по умолчанию 12 секунд; сетевой timeout остаётся 5 секунд. При новом явном выборе A → B предыдущая попытка запуска отменяется логически, освобождает A и не может запускать плеер после B. Это не отмена OkHttp Call.

При ошибке lazy URL на время `call()` устанавливается пустой URL, а временный обработчик `Player.create` запрещает запуск именно этого объекта. Затем подписка снимается и восстанавливается функция разрешения URL для повтора. Успешный переход продолжает использовать обычный контракт LAMPA. Уничтожение плеера отменяет ещё ожидающие lazy-запросы.

Авторизация, выход и заполнение cookie получили независимые scopes и watchdog; прежняя последовательность обмена сохранена. Поиск больше не выключает сохранённый прокси автоматически после 403. Настройки зеркала, cookie, авторизации, качества и истории не очищаются. Новые параметры регистрируют defaults, не перезаписывая существующие значения.

Новый лимит одновременно работающих native HTTP не введён: профилирования на устройстве нет. Скрипт не перезагружает приложение, не меняет DNS и не очищает пользовательские данные.

## Автоматическая проверка

Среда: Node.js `v24.19.0`, Linux. Зависимостей npm нет.

```sh
node --check hdrezka.js
node --test --test-isolation=none tests/*.test.cjs
git diff --check
```

Результат: **50 тестов, 50 passed, 0 failed**. Синтаксис и whitespace-check пройдены. Изоляция тестов отключена из-за ограничений дочернего test runner в рабочей среде; каждый сценарий создаёт собственный VM и fake clock. В обычной среде можно использовать `node --test tests/*.test.cjs`.

Проверены: двойное нажатие; A → B и обратный порядок ответов; потеря callback/clear; raw поздние callback вопреки clear; no callback; ошибки 403/404/429/500; пустое тело, malformed JSON, невалидный/недекодируемый URL; исключения транспорта/парсера; destroy/pause; устаревшие страницы/серии; метаданные без callback; параллельное копирование ссылки; lazy success/error/timeout/cancel/destroy/retry; 20 успешных и 20 прерванных циклов; идемпотентность и смена версии; IP-timeout, двойной push, переход на другой экран; сохранение настроек; proxy/cookie; MP4/HLS, субтитры, история и timeline; авторизация, выход и автоматическое заполнение cookie; отключённая по умолчанию диагностика и отсутствие секретов в её выводе.

**Не выполнены:** запуск Vimu, проверка Xiaomi, живые запросы к HDRezka/прокси, реальный браузерный DOM, профилирование потоков/сокетов, Android-сборка и logcat. Моки проверяют известные форматы HTML, а не актуальную доступность зеркал. Автоматические циклы — модель жизненного цикла, не запуск Android-приложений.

## Установка для ручной проверки

1. Сохранить текущий URL плагина и записать версии LAMPA Android, WebView и Vimu.
2. В LAMPA заменить URL существующего HDRezka-плагина на raw URL `hdrezka.js` из ветки исправления. Не подключать baseline вторым плагином.
3. Перезапустить LAMPA один раз для загрузки новой версии. Это установка обновления, а не автоматический способ восстановления сбоя. Старые анонимные обработчики baseline нельзя снять из нового скрипта; при обновлении из baseline нужен новый JS-контекст.
4. Убедиться в версии `21.10.2026-rezka-v2.2`. В настройках HDRezka доступны «диагностика запросов» (по умолчанию выключена) и «предел ожидания ответа» (10/12/15/30 секунд).
5. Для отката вернуть прежний URL и перезапустить LAMPA; данные не очищать.

Для применения отдельного patch из локальной копии репозитория:

```sh
git switch -c hdrezka-request-lifecycle 60f76e048de7aa95fb61060d44fe948ad98ee3eb
git apply --check /path/to/hdrezka-fix.patch
git apply /path/to/hdrezka-fix.patch
node --check hdrezka.js
node --test --test-isolation=none tests/*.test.cjs
```

## Проверка на TV

Сначала оставить один HDRezka-плагин. Проверить фильмы и сериалы: поиск, оригинальное название при fallback, несколько озвучек, серии/сезоны, качество, субтитры, прогресс, историю, proxy/cookie и внешний Vimu. Затем отдельно вернуть остальные онлайн-плагины и сравнить.

Выполнить 10–20 быстрых открытий/закрытий Vimu, A → B до ответа, уход с экрана до ссылки и переход между фильмами/сериями. При потере ответа после 12 секунд активного JS должно появиться сообщение и снова работать нажатие. Проверить также повтор lazy-серии после ошибки.

При зависании не перезагружать приставку сразу. В отдельных воспроизведениях проверить:

1. Принудительную остановку **только LAMPA**, затем повторный запуск.
2. Принудительную остановку **только Vimu**.
3. Отключение/включение Wi-Fi.
4. «Удержание сокета» включено и выключено как отдельный фактор.

Для каждого опыта записать время, фильм/серию/озвучку, последний `stage`, `state`, `requestId`, pending и действие, восстановившее работу. Если первое действие восстановило работу, влияние следующего проверять на новом воспроизведении, не приписывать ему результат.

При доступном ADB сохранить локально `adb logcat -v time` на время опыта. Не публиковать сырой лог: сама LAMPA/Android upstream логирует URL и параметры вне контроля этого плагина. Новый журнал `HDRezka` содержит только ID, owner, stage, generation, state, elapsedMs и pending, без cookie/паролей/URL/заголовков.

## Остаточные риски и upstream

JS-watchdog ограничивает ожидание при работающем event loop. Android может приостанавливать таймеры WebView в фоне; после возобновления отложенный таймаут выполняется, но это не гарантия 12 секунд реального времени в фоне. Pending в диагностике считает JS-операции, а не открытые native сокеты. Утечки нативного слоя этим патчем не устраняются.

Если сбой сохранится с этой версией, следующий этап начинается со сравнения APK с указанным SHA, сопоставления JS ID с Android ID и счётчиков потоков/соединений. По результатам можно отдельно подготовить закрытие Response в `Get/Post` с тестами 403/404/429/500, oversized body и исключений чтения; уникальный allocator ID в JS-ядре; затем, при необходимости, совместимый capability-gated API отмены в `AndroidJS` с реестром Call и единственным терминальным callback. Изменение pooling и lifecycle Vimu — только после профилирования, отдельно от этих исправлений.
